> 记录真实排查过程（尤其"回放命令到了但手不动"这个案例），并讲解背后常用的工程概念（pkill、并发访问、分层验证等）。
> 面向刚入门 ROS2/嵌入式机器人的人，案例 + 概念都讲明白。

## 一、案例：回放命令"到了"但手不动（完整排查）

### 现象
回放录好的动作（`replay_targets` 发 427 帧），日志显示 hand_controller 收到了目标（`index_mcp 0→61→95°`），但**手没动**。

### 排查全过程（重点看"怎么一步步缩小范围"）

| 步骤 | 做了什么 | 结果 | 排除了什么 |
|---|---|---|---|
| 1 | 看日志确认命令到了 | hand_controller 确实收到目标 | 排除：数据链路、话题 |
| 2 | 查手串口在不在 | `/dev/orcahand_serial` 在 | 排除：手没插 |
| 3 | **直接命令单个关节**（跳过 ROS2，直接调 OrcaHand） | index_mcp 0→18.8°，**手动了** | 排除：手硬件、串口、舵机 |
| 4 | **直接命令全部关节**（模拟 hand_controller 的完整写入） | 0→28.7→47°，**手动了** | 排除：多电机同步写、bus 时序 |
| 5 | 怀疑 hand_controller 实例坏了 → **重启一个全新的** | 再回放，**手动了** ✅ | 定位：旧 hand_controller 实例异常 |

### 根因
旧的 hand_controller 进程（从 launch 起的）在被**反复 pkill + 被诊断脚本并发打开串口**后，进入了异常状态——它"以为"在下命令，实际舵机没收到。**重启一个干净实例就好了**。

### 教训（可复用的方法论）
1. **"命令到了" ≠ "硬件动了"**：日志只证明软件层面到了，必须验证到最底层。
2. **分层排查**：数据链路 → 节点 → 串口 → 舵机，每层单独验证，最快定位。
3. **隔离变量**：绕过 ROS2 直接调硬件（第 3、4 步），把"系统问题"和"硬件问题"切开。
4. **重启是万能的**：长期运行的进程可能悄悄进入坏状态，先重启再深挖。

## 二、排查方法论（通用套路）

排查任何"没反应/卡顿"问题时，按这个顺序：

```
1. 看日志     → 软件层面发生了什么？（命令到了吗？报错吗？）
2. 查资源     → CPU/串口/进程在不在？（ps / ss / ls /dev）
3. 绕开系统   → 直接调底层硬件（绕过 ROS2/中间层），看硬件本身动不动
4. 隔离变量   → 一次只改一个东西，二分法缩小范围
5. 重启干净态 → 怀疑进程坏了就重启，排除"状态污染"
```

> 关键词：**分层验证**（每层都确认）、**隔离变量**（一次一个）、**绕开系统直达硬件**（把问题切成"系统 vs 硬件"）。

## 三、工程概念详解（你问的 + 相关的）

### 3.1 pkill（杀进程）
- `pkill 名字` 按进程名杀；`pkill -f 字符串` 按**完整命令行**匹配杀。
- 例：`pkill -f hand_controller` 会杀掉命令行里含 `hand_controller` 的所有进程。
- ⚠️ **自杀陷阱**：如果用 ssh 远程跑 `pkill -f record_combined`，ssh 自己的命令行里也含"record_combined" → **把自己杀了**（连接断开，报 255）。避免：把命令写进脚本文件再执行，或换个不匹配的模式。

### 3.2 并发访问（串口）
- **串口是独占资源**：一个端口同一时刻最好只有一个进程打开。
- 我之前诊断时，**诊断脚本和 hand_controller 同时打开 `/dev/orcahand_serial`** → 两个进程抢一个串口 → 数据混乱、对方卡住。这就是"并发访问"问题。
- 教训：调试时先**停掉占用串口的进程**，再单独测；测完再恢复。`lsof /dev/ttyACM0` 看谁在占用。

### 3.3 sync write / 多电机写入
- 飞特（FeiTech）舵机支持**一条指令同时写多个电机**（GroupSyncWrite），比逐个写快。
- `set_joint_pos(全关节dict)` 就是一次同步写全部 16 个舵机。
- 排查时特意测了"单个关节写"和"全部关节写"，确认问题不在多电机写入。

### 3.4 僵尸/坏进程状态
- 进程被强杀（pkill/kill -9）后，可能留下**半死状态**或占着资源（串口、端口）。
- 长期运行的进程（ROS2 节点）也可能因为**并发访问、异常信号**进入"看似活着但实际坏了"的状态——它还在收数据、还在打日志，但实际功能已失效。
- 应对：**先重启（干净实例），再考虑深挖**。

### 3.5 会话恢复（session restore）
- 浏览器（Chromium/Chrome）默认在异常关闭后**恢复上次的标签页**。
- 之前板子的 Chromium 被杀后自动重开 HandDriver 网页 → 又占满 CPU。解法：清掉浏览器的 session 文件，或正常退出。

### 3.6 DHCP 与 IP 漂移
- 板子 IP 是 DHCP 动态分配的，重启可能变。
- 排查"连不上板子"先 `ping`，变了就重新找 IP。

## 四、本 session 其它有价值的故障（速查表）

| 现象 | 根因 | 解法 |
|---|---|---|
| 遥操很卡 | 串口每帧全读含 17 次逐电机电流读 | `skip_current` 优化，CPU 85%→45% |

| Jazzy 参数报类型错 | `-p duration:=8`(int) 赋给 double 参数 | 按整数声明，或用统一类型 |
